# Immutable producer observations (step 3.4, part A)

Candidate, non-authorizing, read-only toward every other component. Defined by the hub engineering register step 3.4 (cogno-us/cognous-open-control-stack, `docs/program-v0.2/engineering-register.md`) and hub contract 1.4 (`docs/program-v0.2/s02/contracts/1.4-evidence-handoff.md`). Release and production remain on HOLD.

`observations.py` is an append-only, content-addressed, hash-chained directory of what the Orchestrator observed about its own handoffs (profile `cognous-producer-observation/0`, a candidate wire name). It sits beside the 3.1 handoff in `../lock-driven-handoff/`; it does not change it.

Record members (exactly): `profile`, `schema_version`, `canonical_profile`, `digest`, `observation_id` (`obs_` plus the digest hex), `kind` (closed set: `handoff_envelope_produced`, `handoff_envelope_checked`, `source_revision_observed`, `ci_run_observed`), `subject` (a reference, at most 256 characters), `source_revisions` (sorted unique 40-hex), `lock_digest` (required for the two handoff kinds, null otherwise), `observed_at` (caller-supplied RFC 3339 UTC, `Z`, whole seconds; there is no clock in the module), `sequence`, `predecessor` (digest of the previous record, null for the first), and `execution_standing`, whose exact closed value set is `{hold}` (any other value, including the empty string, a non-string or a different case, is refused as `fixed_field_changed`). The digest is sha256 over the RFC 8785 subset form without `digest` and `observation_id`.

Store behavior: one file per record named by sequence (`000000000001.json`), published by an atomic exclusive hard link so a second writer for the same slot gets `store_conflict`; files are mode 0444 and a writable file is refused on load; every read re-validates each record, canonical bytes, file name and the whole chain (strict JSON, no duplicate keys, no floats); size and count bounds are explicit; symlinks, directories and foreign files are refused. Only the directory the caller names is created or written; no network, no subprocess.

What it does not do: carry or accept a verdict, pass, pin, expectation, grant or authority (such member names are refused as `forbidden_member`, other unknown members as `unknown_member`); select or write a pin; promote anything; or ingest anything into Qualification. Any Qualification ingestion job is Qualification-owned.

Limits (what the directory alone cannot show): replacement or removal of the newest record(s), removal of the whole store followed by a fresh valid chain, and swapping in a different but internally valid chain are all undetectable from the directory alone, because every record only commits to its predecessors. Callers that need to detect them must hold the head digest and/or record count outside the store and pass `expected_head=` / `expected_count=` to `verify_chain` (or `append`); a mismatch is refused as `chain_break`. `expected_head=None` means unchecked (it cannot assert an empty store); `expected_count=0` asserts an empty store; `expected_count` must be a non-negative `int` (a bool is rejected with `ValueError`). On a missing store directory, held values are checked against an empty chain before anything is created. The module does not hold that value for the caller. File modes do not stop a privileged writer; tamper is detected by re-validation, not prevented. Not independently qualified: `tests/integration/producer_observations/` holds developer tests only.

Reading the records:
- `subject` is an opaque reference. Never parse it, split it or derive meaning from its structure. It is plain text without control, format (bidi, zero-width, BOM) or line-separator characters, in NFC, at most 256 characters; it is compared by exact code points.
- `handoff_envelope_checked` records that a check was performed against a lock digest. It records no outcome, and its presence implies no result: a record of that kind does not mean the envelope passed anything.
- `execution_standing` is the fixed value `hold` of this profile. It is a statement about the record itself: nothing is executed, authorized, released or reviewed on its strength, and `hold` does not mean that anything was held, blocked or refused in the world either. Four concepts keep separate names and `execution_standing` is none of them: workflow coordination status (owned by the workflow machine, not this profile), authority outcome (Control Plane decision result), effect observation (independent evidence about what happened) and review decision (the human-review `disposition` of the hub AOI-C01 envelope, `docs/program-v0.2/aoi/aoi-c01-envelope.md`). It must not be read as, mapped to or compared with any of them, and no value of it implies authorization, effect success or review approval. This profile has no member for any of those four.

Rename note (architect decision Q5, step 3.4-A): the member was named `disposition` in the first merged candidate and is now `execution_standing`, before any schema freeze. The member is inside the digest, so every digest, `observation_id` and chain value differs from records of the old shape. A record carrying `disposition` (alone or with `execution_standing`) is refused as `unknown_member`, and a store containing one fails `verify_chain`; there is no in-place migration. The profile name `cognous-producer-observation/0` stays provisional and unfrozen. Successor to [AMENDMENT-PROPOSAL-Q5-execution-standing-rename.md](AMENDMENT-PROPOSAL-Q5-execution-standing-rename.md), which is kept as the historical proposal and still describes the pre-rename state.

Scope of part A: it delivers the observations store only. It does not deliver the source-preserving handoff (that is the sibling O2 branch) and it is not an AOI correlation record. The canonical JSON functions in `observations.py` are a copy that matches the hub `tools/registry_records.py` `jcs_dumps` (an independent reviewer checked equivalence on 20,000 random objects); that is a point-in-time check, not a permanent guarantee, and a later hub change is not followed automatically.
